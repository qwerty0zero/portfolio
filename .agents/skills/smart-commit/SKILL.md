# Скилл: smart-commit (Умное создание одного или нескольких коммитов)

Этот скилл отвечает за анализ изменений в рабочей директории, логическую группировку файлов и создание качественной истории коммитов в соответствии с разделом 5 [AGENTS.md](file:///c:/Users/Admin/WebstormProjects/portfolio/AGENTS.md).

---

## ⛔ Жесткие правила и ограничения (Guardrails)

1. **Язык коммитов — ТОЛЬКО АНГЛИЙСКИЙ**:
   - Все сообщения коммитов (`commit messages`) формулируются **исключительно на английском языке**.
   - Повелительное наклонение в настоящем времени: _"add feature"_, а не _"added feature"_ или _"adds feature"_.
   - Первое слово после типа пишется со строчной буквы, точка в конце заголовка не ставится.
2. **Строго Conventional Commits**:
   - Формат: `<type>(<optional scope>): <description>`
   - Допустимые типы:
     - `feat`: новая функциональность или компонент
     - `fix`: исправление бага или ошибки верстки
     - `refactor`: рефакторинг кода без изменения поведения
     - `style`: стилизация, отступы, правки токенов, форматирование
     - `chore`: конфигурация инструментов, агентские правила, скрипты сборки
     - `docs`: документация, README, комментарии
     - `test`: тесты или тестовые утилиты
3. **Запрет флага `--no-verify`**:
   - **Категорически запрещено** использовать `git commit --no-verify`.
   - Если Husky или `lint-staged` возвращают ошибку при коммите, агент обязан прочитать вывод хука, исправить форматирование/линтер и повторить коммит стандартным путем.

## 🧠 Логика принятия решения: 1 коммит или N коммитов?

Агент **самостоятельно** анализирует `git status --short` и `git diff` и принимает решение о количестве коммитов:

### Когда делать РОВНО ОДИН коммит:

- Все измененные/добавленные файлы относятся к одной логической атомарной задаче (например, создана новая секция `src/components/sections/FAQ.astro` и подключена в `src/pages/index.astro`).
- Все изменения представляют собой единый фикс бага или рефакторинг одной сущности.
- Изменения минимальны по объему (до 3-5 взаимосвязанных файлов).

### Когда РАЗДЕЛЯТЬ на НЕСКОЛЬКО коммитов:

- **Разные слои архитектуры**: одновременное изменение конфигурации сборки (`chore:`), стилей дизайн-системы (`style:`) и компонентов (`feat:`).
- **Базовые UI-компоненты + Секция**: например, сначала создана кнопка `src/components/ui/Button.astro` (отдельный коммит `feat(ui): ...`), а затем секция Hero, которая её использует (`feat(sections): ...`).
- **Смешение рефакторинга/фикса и новой фичи**: случайные правки чужого кода коммитятся отдельно от нового функционала (`fix: ...` затем `feat: ...`).
- **Инфраструктура/Документация**: добавление правил агента (`chore(agents): ...`) отдельно от кода страниц.

## 🔄 Пошаговый алгоритм выполнения

### Шаг 1. Анализ статуса репозитория

Выполнить команду для получения списка всех измененных, добавленных и удаленных файлов:

```bash
git status --short
```

При необходимости просмотреть точный дифф:

```bash
git diff
```

### Шаг 2. Группировка и план коммитов

Агент составляет внутренний план:

- Список коммитов (1 или несколько).
- Для каждого коммита: точный список файлов и текст сообщения на английском.
- Пример плана:
  1. `git add src/components/ui/Button.astro` -> `feat(ui): add reusable button component`
  2. `git add src/components/sections/Hero.astro src/pages/index.astro` -> `feat(hero): implement landing hero section`

### Шаг 3. Поэтапный `git add` и `git commit`

> [!IMPORTANT]
> Никогда не используйте огульный `git add .`, если запланировано несколько коммитов! Индексируйте (`git add`) строго файлы текущей логической группы.

Выполнить коммит:

```bash
git add <пути_к_файлам_первой_группы>
git commit -m "<type>(<scope>): <clear english summary>"
```

### Шаг 4. Обработка Pre-commit хуков

- Если хук `lint-staged` успешно прошел — коммит создан.
- Если хук упал с ошибкой линтинга или форматирования:
  1. Внимательно изучить текст ошибки в выводе терминала.
  2. Исправить проблемные строки в файлах (или запустить `pnpm run fmt`).
  3. Снова добавить файлы через `git add <файлы>`.
  4. Повторить `git commit` **без флага `--no-verify`**.

### Шаг 5. Повторение для оставшихся групп

Повторить шаги 3–4 для каждого запланированного коммита.

### Шаг 6. Финальная верификация

Убедиться, что рабочая директория чиста, и вывести созданные коммиты:

```bash
git status
git log -n <количество_созданных_коммитов> --oneline
```
